Compatibility & privacy

The secret is encoded as SQL nvarchar (UTF-16LE), hashed with SHA-256, then used as the HMAC-SHA256 key for patient| plus your exact value in UTF-16LE (also SQL nvarchar). Output is 64 uppercase hexadecimal characters. Values are not trimmed, case-folded or converted to a number.

Plain positive decimal IDs such as 12345 still match your SQL export with @EncryptPatientIDs = 1. Leading zeroes, spaces, signs and arbitrary text now have their own keys; the original SQL converts numeric IDs to canonical decimal text. The current SQL exports accept positive integer IDs; this page additionally supports exact text values.

Compatibility correction: older versions of this page hashed the message as UTF-8 and did not match these SQL exports. Regenerate any keys made with that version from the original IDs; do not hash existing keys.

An empty single value can be hashed. Empty CSV cells are left blank so missing IDs are not assigned a shared linkage key. Use original values, not already-generated keys.

These are pseudonyms, not anonymous data. Protect the secret: anyone who knows it can test possible IDs. Use separate secrets for projects that should not be linked. Other identifying fields can still reveal a person.

The page does not save inputs or send them to a server. Clear all removes inputs and results from the page, but cannot erase clipboard contents or downloaded files. Use a trusted browser and device.

Use the upload icon in the passphrase field to load a UTF-8 .txt file (12–200 characters after trimming, up to 4 KiB). Trailing whitespace, including spaces, tabs and newlines, is removed. Leading and internal characters are preserved; leading spaces and embedded line breaks are rejected. The loaded passphrase is locked against edits.
